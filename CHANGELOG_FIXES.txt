Smart Accommodation — fixes in this package

1. Homepage attraction photo paths now use uploads/attractions/ for filename-only values, rather than the accommodation-photo directory. Legacy attraction paths incorrectly prefixed with uploads/accommodations/ are redirected to the attractions folder. Missing photos still use a local fallback image.
2. OpenStreetMap discovery searches more tourism, historic, nature, recreation, landmark and cultural categories. Imported places still enter the admin review queue; they are not published until approved. If an OSM record includes a direct HTTPS image URL in an image tag, it can be stored as the attraction photo; most records will still need an admin-uploaded photo.
3. Host and admin dashboards now have an explicit View Website link. Hosts already have a View live action for approved property listings.
4. Tourist and host profile pages include a password-confirmed Close account action. This is a soft closure, not hard deletion: historical bookings, reviews and payment records remain. Closing a host account suspends approved listings. Admins can restore a closed account from user management.

REQUIRED DATABASE STEP FOR ACCOUNT CLOSURE
Before testing the Close account feature, open phpMyAdmin, select the smart_accommodation database, choose Import, and import database/migration_account_closure.sql. This adds users.account_closed_at. Run this migration only once. Do not import it repeatedly.

Validation
All PHP files in this package passed PHP syntax checks. The application was not connected to the user's live MySQL database or browser in this environment, so runtime workflows still need to be tested locally.

2026-11-14 — v9.21 Commission controls
- Rates are editable by the admin: Admin > Rates & settings (admin/settings.php) sets the commission %, the guest service fee %, the days a host has to pay, and the payment instructions. Values are stored in the new platform_settings table. includes/config.php now only supplies the defaults used until the admin saves a value. New rates apply from then on; existing ledger rows and bookings keep the rate they were created with.
- Overdue enforcement: a commission that has been owed (status "accrued", not yet reported) for more than the configured days makes the host overdue. Overdue hosts are hidden from search, the homepage and nearby lists, their listing pages and booking page refuse new bookings, and the host sees a "listings paused" notice on the dashboard and commission page. Nothing is changed in the listing's own status: it returns automatically when the host reports payment or the admin marks it received. Existing bookings are not affected. Setting the days to 0 turns this off. The ledger is refreshed automatically (at most every 5 minutes) so enforcement does not depend on someone opening a finance page.
- Refunds of settled commission: if a stay is cancelled (or the payment reversed) after its commission was settled, the ledger row is marked "refund due" for the full commission plus service fee. Admin > Revenue lists these; the admin records the refund (amount up to the full figure, plus reference) or declines it with a reason. The host sees the status on the Commission page. Rows still accrued are voided as before. The money itself is still sent outside the site; the site records it.
- Database: platform_settings table and commission_ledger.refund_* columns are created automatically. database/migration_v9_21_commission_controls.sql does the same by hand if preferred.


2026-11-14 — v9.22 Booking numbers no longer exposed
- The numeric booking_id (and the "#BK00012" label built from it) was shown on pages, in URLs, in hidden form fields and in emails, so booking numbers could be counted and guessed. Every page already checked that a booking belongs to the signed-in guest, host or admin, so other people's bookings could not be opened; this removes the guessable number as a second layer.
- Each booking now has a random public reference, e.g. BK-K7M2QX9TPA (new column bookings.booking_ref, unique, created and back-filled automatically). Pages, links, forms, emails, the receipt, the evidence pack and the admin search use it. URLs use ?ref=..., forms post booking_ref. Numeric ids are no longer accepted in URLs or forms.
- New file includes/booking_ref.php (loaded by includes/db.php): bookingRef(), bookingLabel(), bookingIdFromRef(). New bookings get their reference in tourist/book.php.
- Old emails that contain a payment link with ?booking_id=12 will land on My bookings instead of the payment page; the guest can open the booking from there.
- Not changed: payment_id (receipts, proofs) and ledger/remittance ids still appear in a few admin/host links. They are checked for ownership on every request but are still sequential numbers.


2026-11-14 — v9.23 Payment, receipt and commission numbers no longer exposed
- Payment ids, commission-ledger ids and commission-payment (remittance) ids are no longer shown in URLs, forms, links or page markup. They are replaced by opaque tokens (the id encrypted and authenticated with a secret key that the site generates once and keeps in platform_settings as id_token_key). Tokens cannot be guessed, edited, or used for a different kind of record, and need no extra database column. Numbers are no longer accepted: receipt.php?pid=..., proof.php?type=...&ref=..., and form fields payment_ref, ledger_ref, ledger[] and remittance_ref.
- Receipt numbers are no longer the payment id (RC-000012). They are now a short code derived from it with the secret key (for example RC-L6ONNTSOUY). Receipts printed before this change show the old number; the receipt verification code is unchanged.
- Old links in earlier emails (receipt.php?payment_id=...) now show "Receipt not found"; the guest can open the receipt from My bookings.
- Keep the id_token_key row in platform_settings when you move or restore the database; if it is lost a new key is made and old links stop working.
- Not changed: admin-only ids (users, incident reports, reviews, listings) and public listing ids in URLs (details.php?id=...).


2026-11-14 — database/schema.sql (full structure)
